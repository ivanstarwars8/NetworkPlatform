# Мост Xray: путь пакетов через TUN и производительность на Linux

Дата: 2026-11-27. Мост — `Cores/Bridge` (ветка `stage2/bridge`), Xray-core v26.11.9 (`676eaf66f8f0`), Go 1.27.4.

Пометки: **[M]** — измерено нами, команда и сырой результат указаны; **[V]** — видно в исходнике (путь
указан); **[U]** — не проверено.

Всё ниже получено на сервере разработки (linux/amd64, 5 vCPU, общий с рабочими сервисами, load average
3,5–4,5 во время всех прогонов). На Apple ничего из этого не запускалось.

## 1. Стенд

`Cores/BuildScripts/bridge-tunlab.sh` создаёт два одноразовых сетевых пространства имён и ничего не меняет
в основном (интерфейсы, маршруты, межсетевой экран); после каждого режима пространства удаляются, лишних
процессов не остаётся (скрипт проверяет `pgrep`).

```
ns C (клиент)                                             ns S (сервер)
приложение (nplab client, сокеты ядра Linux)
   │  маршрут по умолчанию v4/v6 → nptun0                 dummy «tg»: 203.0.113.1  — штатный xray (сервер)
   ▼                                                                 198.18.0.10, 2001:db8:1::10 — цели
nptun0 (tun ядра, IFF_NO_PI, MTU 1280/1400/1500)                     198.18.0.53, 2001:db8:1::53 — DNS
   │ read()/write() по пакету                              цели: echo 7, discard 9, sink 10, source 19,
   ▼                                                             DNS 53 и 5353 (UDP), TLS 8443 (цель REALITY)
насос nplab (замена NEPacketTunnelFlow)
   │ TunWrite(пачка) / TunRead(буфер) — API engine
   ▼
мост → ядро Xray → outbound ──── veth vc ── (исключающий маршрут 203.0.113.1/32 via vc) ── vs ───┘
```

- **Режим `flow`** (основной путь, ADR-0001 §4.1): насос читает пакеты из tun ядра и отдаёт мосту пачкой
  до `-batch` пакетов (`engine.TunWrite`), обратно забирает пачки `engine.TunRead` и пишет в tun по одному
  пакету. [V: `Cores/Bridge/cmd/nplab/bridge.go`]
- **Режим `fd`**: дескриптор того же tun передаётся мосту, ядро читает его само (`xray.tun.fd`).
- **Штатный xray**: тот же бинарник ядра, собранный из того же закреплённого модуля
  (`go build github.com/xtls/xray-core/main`), получает дескриптор того же tun через `nplab tunexec`
  (тот же путь `xray.tun.fd`) и **тот же файл конфигурации**, что и мост.
- Конфигурации клиента: VLESS+REALITY+Vision (`reality`) и Shadowsocks 2022 `2022-blake3-aes-128-gcm`
  (`ss`). Голый VLESS по TCP на публичный адрес ядро запрещает («vless without TLS … is prohibited»), поэтому
  второй конфигурацией взят Shadowsocks. В конфигурации включены stats и счётчики — мост включает их всегда,
  для честного сравнения штатный xray получает то же.
- Сборки — release: `go build -trimpath -ldflags='-s -w'`, оба бинарника одним Go 1.27.4.

### Что этот стенд доказывает и чего не доказывает

Доказывает: путь `приложение → стек TCP/IP ядра Linux → tun → TunWrite → стек ядра Xray → outbound →
сервер → цель` и обратно работает для TCP и UDP по IPv4 и IPv6, для DNS, при MTU 1280/1400/1500, с
фрагментацией, ограниченными очередями, без петли; стоимость моста против штатного xray на одном и том же
устройстве tun.

Не доказывает:
- Насос — Go-код в том же процессе, вызов `engine.TunWrite` — обычный вызов Go, **перехода C↔Go (cgo) и
  Swift нет**. Цена перехода измерена отдельно C-тестом (`bridge-linux-cabi-test.sh`: десятки нс на пакет в
  пачке, `tun-integration.md` §3) и на фоне 1,5–4,5 мкс работы стека на пакет (§4) мала, но на arm64 не
  мерялась. [U]
- `NEPacketTunnelFlow.readPackets` отдаёт пачки, размер которых решает система; здесь насос сам набирает
  пачку из того, что уже лежит в tun (в среднем 2,5 пакета при загрузке, 50 при отдаче, §4). На Apple
  размеры будут другими. [U]
- Запись в tun ядра Linux — один пакет на `write()` (12–17 мкс на пакет здесь); `writePackets` на Apple
  принимает массив. Стоимость обратного направления на устройстве другая. [U]
- Исключение собственных сокетов из туннеля на Linux делает маршрут (аналог `excludedRoutes`), на Apple —
  по утверждению Apple, сама NetworkExtension для процесса-провайдера. Проверено только то, что ядро
  ходит к серверу по таблице маршрутизации системы и мост сам ничего в туннель не заворачивает. [U для Apple]
- Стек TCP/IP на стороне приложения — Linux, не iOS/macOS: его поведение ACK, окна, PMTU другое.
- Память и CPU — процесс Linux на x86-64; `phys_footprint` расширения iOS не измерялся (E-4).

Ограничения ядра, найденные этим прогоном (одинаковы у моста в `flow`, `fd` и у штатного xray, то есть
к мосту не относятся): [M]

1. **UDP через VLESS+REALITY+Vision: датаграмма 7500 байт проходит, 7600 и больше — теряется**, по IPv4 и
   IPv6, у штатного xray так же. Прежний тест моста «UDP 8000 байт» шёл без прокси (стек к стеку) и этого не
   видел. Причина не разбиралась [U: вероятно, предел буфера ядра `buf.Size` = 8 КиБ с заголовками]. Для
   QUIC (≤ 1350) не важно; для DNS через UDP с EDNS-ответами больше 7,5 КБ — важно.
2. **TCP half-close не передаётся.** Приложение закрывает запись (FIN) и ждёт ответа сервера, который
   отвечает только после FIN: через прокси соединение закрывается через ~1 с без ответа (политика ядра
   `downlinkOnly` = 1 с; FIN по VLESS не доходит до цели). Напрямую — работает. Тестовые протоколы стенда
   поэтому передают длину заранее (порты sink 10 и source 19) и не зависят от half-close.
3. **Скорость загрузки (сервер → приложение) упирается в ~200 Мбит/с** во всех трёх вариантах и на обоих
   протоколах, а отдача — 800–1000 Мбит/с (§3). Причина не найдена. Проверено и исключено: управление
   перегрузкой и qdisc в клиентском пространстве (`cubic`+`pfifo` вместо `bbr`+`fq` — без изменений),
   отложенные ACK (`quickack` — без изменений), насос моста (поток записи занят 30 % времени, у штатного
   xray насоса нет вовсе), число соединений (4 потока дают ту же сумму). В прежнем тесте «стек ядра Xray
   против второго экземпляра того же стека» (без tun ядра Linux) загрузка давала 740–810 Мбит/с, так что
   потолок возникает на стыке стека ядра Xray со стеком Linux через tun. [U]

## 3. Пропускная способность, задержка, CPU, память (`bridge-tunlab.sh bench 7`)

Методика:
- 7 раундов, внутри раунда варианты чередуются (direct-veth, direct-loopback, затем для каждой конфигурации
  stock → flow → fd), чтобы дрейф нагрузки сервера распределялся по всем вариантам.
- Клиент (xray или мост) запускается заново в каждом раунде; перед замерами — прогрев 16 МиБ (первое
  рукопожатие REALITY ≈ 5 с из-за пробы цели на сервере, `README.md` моста).
- Тесты: TCP 64 МиБ вниз (1 и 4 соединения) и вверх; `tcp-rr` — 2000 обменов по 1 байту в одном соединении;
  `udp-rr` — 2000 обменов по 64 байта; `tcp-setup` — 100 новых соединений до первого байта эха (включает
  рукопожатие outbound с сервером).
- CPU — `utime+stime` процесса клиента из `/proc/<pid>/stat` за время теста; RSS — пик по опросу каждые
  50 мс; показатели рантайма Go моста — разность двух снимков `/sample` (runtime/metrics) до и после теста.
- Статистика по 7 прогонам: медиана, p95 (ближайший ранг; при n = 7 это максимум), min, max, CV.
  Полная таблица — `Benchmarks/results/bridge-2026-11-27/bench-summary.md`, сырьё — `bench.jsonl`.

## 4. Стоимость пути пакета по размеру пачки (`bridge-tunlab.sh batch 5`)

Shadowsocks 2022, MTU 1500, 5 прогонов на размер, медиана [min–max]. «Мост» здесь — время внутри
`engine.TunWrite` / `engine.TunRead`; «write()» — системный вызов записи в tun ядра Linux. [M]

| `-batch` | вверх, Мбит/с | CPU процесса, мкс/пакет (вверх) | `TunWrite`, нс/пакет (вверх) | вниз, Мбит/с | `TunRead`, нс/пакет (вниз) | write() в tun, нс/пакет (вниз) |
|---|---|---|---|---|---|---|
| 1 | 593 [451–670] | 19,3 | 3369 | 195 | 777 | 13472 |
| 4 | 809 [492–1249] | 14,5 | 2281 | 196 | 533 | 11904 |
| 16 | 1214 [747–1431] | 12,4 | 1461 | 190 | 443 | 13071 |
| 64 | 767 [719–1121] | 11,9 | 1571 | 197 | 450 | 11831 |

- `TunWrite` 1,5–3,4 мкс на пакет — почти целиком работа стека ядра Xray (`stack.Input` → TCP →
  доставка данных обработчику); разбор кадров моста в профиле CPU не виден отдельной строкой.
- `TunRead` 0,4–0,8 мкс на пакет — копирование из кольца моста в буфер вызывающего.
- Пачки помогают отдаче: CPU на пакет падает на 38 % от 1 к 64; пропускная способность растёт с 593 до
  767–1214 Мбит/с (разброс большой). На загрузке пачки записи маленькие сами по себе (в tun лежат только
  ACK, в среднем 2,5 пакета), а пачки `TunRead` — 47–57 пакетов, размер `-batch` на них не влияет.
- Самая дорогая часть пути на Linux — `write()` в tun ядра, 12–13 мкс на пакет; на Apple его заменяет
  `writePackets` с массивом, цена неизвестна. [U]

конфигурации, буфер пачки насоса стенда (0,56 МиБ).

### Что из профилей следует для оптимизации

Код моста занимает около 5 % CPU (почти всё — копирование пакетов в кольце) и не выделяет память на пакет. Единственный заметный его вклад — два
копирования пакета в направлении «ядро → хост» (в кольцо при `WritePacket` и из кольца в `TunRead`).
Убрать первое можно только отказом от кольца с хвостовым сбросом (стек ядра пишет пакет синхронно и не умеет
ждать), второе требует C ABI — буфер принадлежит вызывающему. Выигрыш — часть из этих 5 %, при этом теряется
ограниченность очереди. **Профили оптимизацию моста не оправдывают; код не менялся.** Узкие места —
системные вызовы tun ядра Linux (на Apple другие), криптография и стек ядра Xray.

## 6. Долгий прогон: память и горутины (`bridge-tunlab.sh soak 30`)

Нагрузка: REALITY, режим `flow`, 4 рабочих потока; каждый в цикле открывает новое TCP-соединение и
скачивает 1 МиБ, открывает ещё одно и отдаёт 1 МиБ (оба — с темпом ~1 МиБ/с), затем открывает новый
UDP-сокет и делает 5 обменов. Снимок `/sample` каждые 30 с. Рантайм Go не настраивался (лимит памяти и
GOGC — по умолчанию). Сырьё — `soak-flow-30min-samples.jsonl`. [M]

Итог 30 минут: 7,25 ГБ, 6918 TCP-соединений, 17295 UDP-обменов, ошибок 0, потерь UDP 0; CPU моста 257,5 с
(14 % одного ядра), из них GC 12,1 с (4,7 %), 64 цикла GC; очередь `TunRead` — пик 364 КБ из 2 МиБ,
отброшено 0.

**Память выходит на плато через ~10 минут и дальше 20 минут не растёт** (живая куча 52,3–53,5 МиБ,
горутины 3369–3439): утечки в мосте нет. Но плато высокое, и причина установлена по дампу горутин в конце
(`soak-flow-30min-goroutine.txt`): 1059 UDP-сессий, каждая — три горутины (`proxy/tun.(*udpConn)` ждёт
пакет, outbound VLESS читает XUDP из своего соединения REALITY с сервером, копирование вверх), то есть ещё и
открытое TCP-соединение к серверу на каждую. Приложение закрыло свой UDP-сокет, но у UDP нет сигнала
закрытия, и ядро держит сессию по таймауту `connIdle` политики (по умолчанию 300 с). Новых UDP-потоков было
1,9 в секунду (3459 за прогон), значит сессия живёт ≈ 560 с после последнего пакета — около двух `connIdle`
(по-видимому, таймер стека tun и таймер outbound срабатывают друг за другом [U]); с `connIdle` = 30 с то же
отношение даёт ≈ 62 с (≈ 120 сессий при 1,9 потока/с, ниже). На сессию приходится
≈ 46 КиБ живой кучи плюс ≈ 27 КиБ стеков. Профиль кучи в конце (`soak-flow-30min-heap-inuse-top.txt`, 54 МБ):
состояние uTLS-клиента REALITY (`UConn.ApplyPreset`) — 21 %, ключи ML-KEM-768 гибридного обмена отпечатка
`chrome` — 13 %, буферы `bytespool` ядра — 18 %; моста там — 2 МиБ кольца `newPacketQueue`.

Это поведение ядра, а не моста:
- штатный xray под той же нагрузкой (8 минут, `soak 8 stock`) растёт с той же скоростью: RSS 31,9 → 99,7 МиБ
  за 5 минут и 137 МиБ к 8-й минуте (мост: 32 → 116 МиБ за 6 минут), `soak-stock-samples.jsonl`;
  `proxy/tun/handler.go:171` ставит стеку `IdleTimeout` = `connIdle` уровня пользователя, мост делает то же
  (`engine/flowtun.go`, `newFlowInbound`) [V];
- с `connIdle` = 30 с (`CONNIDLE=30 … soak 6 flow`) плато наступает за 90 с: живая куча 9,7–10,0 МиБ,
  380–397 горутин, RSS 57–59 МиБ (`soak-flow-idle30-samples.jsonl`).

Вывод для iOS (бюджет расширения ~50 МиБ, ADR-0001): при умолчаниях ядра каждый короткий UDP-поток
приложения обходится в ~73 КиБ на ~10 минут, и сотня-другая таких потоков в минуту (QUIC, игры, мессенджеры;
DNS здесь идёт через outbound `dns` и прокси-соединений не создаёт [U: время жизни самой UDP-сессии в стеке
для DNS не мерили]) займёт десятки мегабайт. Компилятору конфигурации нужно задавать `connIdle` заметно
меньше 300 с (цена: простаивающие дольше TCP-соединения тоже будут закрываться) или ядро должно получить
отдельный таймаут UDP; это решение вне моста, записано как открытый вопрос. На устройстве не проверено.

Продолжение — `memory-budget.md`: профиль `mobile` (`connIdle` 30 с, GOGC 25, предел 40 МиБ) даёт под этой же
нагрузкой плато RSS 48–49 МиБ (RssAnon 20 МиБ).

## 7. Гонки, утечки, взаимоблокировки [M]

- **e2e под детектором гонок** (`NP_LAB_RACE=1 … build`, затем `e2e`; мост и насос собраны с `-race`, штатный
  xray — без): все проверки дали те же результаты, что и release-сборка (провалились только 7 ожидаемых:
  half-close ×2, предел UDP ×4, контроль петли ×1). Детектор сообщил 9 гонок в режиме `flow` и 2 в режиме
  `fd` — все одна и та же гонка **внутри ядра**: `proxy.XtlsFilterTls` (`proxy/proxy.go:629`) пишет общий
  `TrafficState`, `VisionReader.ReadMultiBuffer` (`:255`) и `VisionWriter.WriteMultiBuffer` (`:357`, `:384`)
  читают его без синхронизации. Ни в одном из доступов нет кадров моста или насоса. Это та же гонка, что
  уже записана в `Cores/Bridge/README.md`; исправлять её надо в ядре.
- **Утечки**: за 30 минут память и горутины вышли на плато и не росли 20 минут (§6). После остановки движка
  горутины возвращаются к исходным — проверено ранее 200 циклами start/stop (`TestStartStopCycles`).
- **Взаимоблокировки**: ни одна остановка клиента (моста или штатного xray) за все прогоны стенда не потребовала `SIGKILL` (скрипт
  ждёт 10 с и пишет в журнал, если пришлось убивать); `TunRead`, ждущий пакета, просыпается при остановке.
- **Полный набор `go test -race -count=1 ./...`** со штатным xray как сервером (`NP_STOCK_XRAY`), Go 1.27.4:
  `go vet` чист, `gofmt` чист; все тесты проходят, кроме `TestFlowThroughProxyWithDNS` — он падает
  на той же гонке ядра в Vision (1 отчёт, `VisionWriter.WriteMultiBuffer`; кадров моста в доступах нет), как и
  в прошлых прогонах. Тот же тест под `-race` через Trojan+TLS и VLESS+XHTTP (`NP_TEST_FLOW_PROXY`) проходит.
  Итог набора — **FAIL** из-за гонки ядра; в мосте гонок, утечек и взаимоблокировок не найдено.

## 8. Как повторить

На Linux-машине с root, Go и iproute2, из корня репозитория:

```sh
Cores/BuildScripts/bridge-tunlab.sh build          # release-сборки nplab и штатного xray
Cores/BuildScripts/bridge-tunlab.sh e2e            # §2, ~4 мин
Cores/BuildScripts/bridge-tunlab.sh bench 7        # §3, ~9 мин
Cores/BuildScripts/bridge-tunlab.sh batch 5        # §4, ~3 мин
Cores/BuildScripts/bridge-tunlab.sh profile        # §5
Cores/BuildScripts/bridge-tunlab.sh soak 30        # §6
python3 Benchmarks/BridgeBench/summarize.py Logs/tunlab/bench.jsonl > summary.md
NP_LAB_RACE=1 Cores/BuildScripts/bridge-tunlab.sh build && Cores/BuildScripts/bridge-tunlab.sh e2e   # e2e под -race
```

Результаты пишутся в `Logs/tunlab` (`NP_LAB_OUT`), одна JSON-строка на тест.
