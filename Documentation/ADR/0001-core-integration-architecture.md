# ADR-0001. Интеграция движков: один активный движок на Packet Tunnel

- Статус: **принято**, с условиями проверки на Mac (раздел 7)
- Дата: 2026-11-24; раздел «utun» пересмотрен 2026-11-25 (§4.1)
- Основание: `RESEARCH.md`, `Documentation/Research/xray.md` §6, `Documentation/Research/singbox.md` §3 и §8, `PLATFORM_MATRIX.md` §3, `LICENSE_AUDIT.md` §5

## 1. Контекст

Платформа должна работать с двумя Go-движками — sing-box и Xray-core — как со сменными. Оба умеют читать utun напрямую (для Xray это больше не основной путь, §4.1), оба допускают один экземпляр на процесс, оба настраивают сборщик мусора и лимит памяти на весь Go-рантайм. Расширение Packet Tunnel на iOS живёт в недокументированном бюджете памяти около 50 МиБ.

Ничего из перечисленного ниже не собиралось и не запускалось. Решение принято по исходникам и документации.

## 2. Варианты

### A. Единый Go-мост: один модуль, оба ядра, один рантайм, одно расширение

За:

- одно расширение, один XCFramework;
- конфликтующих путей модулей у форков не найдено, коллизий собственных `.proto` не найдено. [V]

Против:

- нужен Go ≥ 1.27.3 (libXray), а sing-box upstream собирает на 1.26.10 и держит 62 `go:linkname` с `-checklinkname=0`. Соберётся ли и заработает ли — неизвестно; [U]
- MVS поднимет sing-box около 20 общих модулей, включая grpc 1.79.1 → 1.85.0 и go-proxyproto 0.8.1 → 0.16.0; [V — версии, U — последствия]
- `init()` обоих ядер выполняются всегда; два QUIC-стека, два uTLS, два gVisor, два WireGuard в одном процессе; [V — структура, U — мегабайты]
- процесс-глобальные настройки конфликтуют: тюнинг GC libXray против `SetMemoryLimit` libbox; `godebugDefault=multipathtcp=0,tlssha1=1` применится и к Xray; [V]
- обновление любого ядра требует повторной проверки всего графа;
- бинарник целиком становится GPL-3.0 (MPL §3.3) — Xray-линейка теряет лицензионную чистоту; [V — текст, U — вывод]
- паника одного ядра роняет общий процесс.

### B. Два независимо собранных Go-фреймворка в одном процессе расширения

Против: README libXray прямо называет это неподдерживаемым со ссылками на golang/go#18976, golang/go#15956, XTLS/libXray#116. [V — текст; отказ не воспроизводился]. Память — как в варианте A или хуже.

За: ничего, чего не давал бы вариант C.

### C. Отдельные расширения: одно ядро — один артефакт — один процесс

За:

- каждое ядро собирается штатной цепочкой своего upstream, своим Go;
- в памяти только активное ядро;
- сбои изолированы;
- ядра обновляются независимо;
- сборка без sing-box возможна без изменения control plane.

Против:

- допустимость двух packet-tunnel-расширений в одном iOS-приложении не проверена; [U]
- два XCFramework: Go-рантайм и общие модули на диске дважды;
- смена движка — перезапуск туннеля (но это так в любом варианте: оба ядра однократны в процессе).

## 3. Решение

**Вариант C.** Вариант B отклонён окончательно. Вариант A отклонён и не закладывается в архитектуру; вернуться к нему можно только после сборочного эксперимента (раздел 7, E-7) и только если владелец согласен на GPL-3.0 для всего бинарника.

Правила:

1. **Один движок на процесс Packet Tunnel.** Расширение линкует ровно один Go-артефакт. Горячей смены движка нет: смена — остановка туннеля и запуск другого расширения.
2. **Приложение не линкует Go.** Ни libbox, ни мост Xray. Разбор профилей, валидация и компиляция конфигурации — на Swift (ADR-0002). Этим мы сознательно расходимся с sing-box-for-apple и hiddify, которые держат Go-рантайм в приложении.
3. **Набор движков — измерение сборки, а не константа архитектуры.** Control plane работает со списком установленных движков и не знает, сколько расширений в бандле.

   | Вариант сборки | Расширения | Назначение |
   |---|---|---|
   | `XrayOnly` | одно, Xray | кандидат в App Store без GPL-кода; базовый вариант разработки |
   | `SingBoxOnly` | одно, sing-box | запасной вариант, если два расширения в одном приложении недопустимы |
   | `Dual` | два | каналы, где GPL для всего продукта приемлем (решение владельца, ADR-0006) |

   Поправка 2026-11-27 (ADR-0007): второй движок — Mihomo. Вариант `SingBoxOnly` переименован в `MihomoOnly`, `Dual` = Xray + Mihomo. Так они названы в `Apps/Configurations/`.

4. **Техническая и лицензионная границы — разные вещи.** Разделение по процессам решает память, сборку и изоляцию. Оно **не** делает `Dual` свободным от GPL: `LICENSE_AUDIT.md` §5 считает отдельный процесс внутри одного `.app` ненадёжной границей. Свободен от GPL только вариант, в котором sing-box нет вовсе.
5. **Выбор расширения** — через `NETunnelProviderProtocol.providerBundleIdentifier`. Одна VPN-конфигурация, идентификатор провайдера переписывается при смене движка. Если это не работает (E-3) — по одной конфигурации на движок.

## 4. Как подключается каждый движок

### Xray-core: собственный C-мост

- Отдельный Go-модуль в репозитории с закреплёнными версиями Xray-core и Go. Сборка `go build -buildmode=c-archive` по образцу `libXray/build/app/apple_go.py`, затем XCFramework.
- libXray как зависимость не используется: в его `Invoke` нет потоков статистики и логов, тюнинг памяти (30 МиБ, GC 10 %, `FreeOSMemory()` каждую секунду) зашит и не откатывается, версии в его сборке не закреплены. Его код под MIT, заимствовать фрагменты можно.
- Мост вызывает `core.NewWithContext`/`Start` напрямую и экспортирует наш C ABI (`Cores/Bridge/cabi`): проверка конфигурации, запуск, остановка, перезагрузка (stop + start), состояние, снимок статистики, чтение журнала из ограниченной очереди, параметры памяти, пакетная передача пакетов. Реализован и проверен на Linux (2026-11-25); под Apple не собирался.
- Пакеты мост получает по §4.1: основной путь — пачки из `NEPacketTunnelFlow`, запасной — дескриптор utun, который мост сам кладёт в окружение под ключом `xray.tun.fd` (`common/platform/platform.go:27`). Swift JSON конфигурации ни в одном из режимов не правит.
- gomobile не нужен. Это единственный путь к tvOS для Xray (gomobile-сборка libXray tvOS не поддерживает) и наиболее вероятный путь к visionOS.

### sing-box: libbox как есть

- `gomobile bind` форком SagerNet, тулчейн и флаги — как в `cmd/internal/build_libbox/main.go` и CI upstream, включая патч `internal/cpu` и обязательные `-ldflags`.
- Сокращённый набор тегов. Исходная позиция: без `with_naive_outbound`, `with_tailscale`, `with_usbip`, `with_openvpn`, `with_openconnect`. У каждого тега есть заглушка в `include/`. [V] Окончательный набор — после измерения размера и памяти.
- Swift-адаптер реализует `PlatformInterface`; большинство методов — заглушки.
- Закрепляемая линия (1.14.x или 1.15) выбирается после сверки тегов upstream: аудит сделан по альфе, а сведения о текущей стабильной версии расходятся (`RESEARCH.md` §3, п. 5).

### Общее для обоих

- **utun.** См. §4.1: для Xray основной путь — документированный `packetFlow`; дескриптор нужен sing-box и остаётся опцией для Xray.
- **Сетевые настройки туннеля** (`NEPacketTunnelNetworkSettings`: адреса, маршруты, DNS, MTU) задаёт Swift. MTU — параметр адаптера: sing-box под NE по умолчанию 4064, Xray — 1500.
- **Сторож.** Движок остановился сам → `cancelTunnelWithError`.
- **Сериализация.** Все вызовы движка идут через один выделенный исполнитель; счётчик поколений отсекает запоздавший старт после stop.
- **Остановка.** Завершение процесса расширения — только аварийный путь после тайм-аута чистой остановки.

### 4.1. utun: дескриптор или packetFlow (решение 2026-11-25)

Основание: `Documentation/Architecture/tun-integration.md` (исходники Xray-core v26.11.9, измерения на Linux).

Факты:

- Публичного API, отдающего файловый дескриптор utun, у `NEPacketTunnelProvider` нет. [U] Оба известных способа его добыть недокументированы: KVC `packetFlow.socket.fileDescriptor` — приватный API; перебор дескрипторов с `getpeername` и сравнением с `com.apple.net.utun_control` — публичные системные вызовы, но опора на внутреннее устройство NetworkExtension (приём WireGuardKit, MIT). Риск R-08.
- Xray-core экспортирует свой стек отдельно от устройства: `tun.NewStack` + `Stack.Input(packet)` + интерфейс `tun.Tun`. [V: `proxy/tun/stack.go`, `proxy/tun/tun.go`] Значит, пакеты можно подать из `NEPacketTunnelFlow`, не имея дескриптора и не добавляя tun2socks.
- Пакетная передача делает переходы Swift↔Go дешёвыми: измерено 32–35 нс на пакет при пачке 64 против 258–266 нс при вызове на каждый пакет (C→Go, Linux/amd64); один TCP-поток через весь путь — 1,05–1,2 Гбит/с. [измерено, `tun-integration.md` §3]

Решение:

1. **Xray: основной путь — `NEPacketTunnelFlow.readPackets`/`writePackets` с пакетной передачей в мост** (режим `tun.mode = "flow"`). Приватные API не используются. Мост регистрирует собственный inbound поверх стека ядра вместо `protocol: "tun"` из конфигурации; конфигурация для обоих режимов одна.
2. **Путь через дескриптор (`tun.mode = "fd"`) остаётся опцией моста**, выключенной по умолчанию. Включается после проверки на устройстве (E-5) и только через перебор дескрипторов публичными системными вызовами. KVC-путь из проекта исключён.
3. **sing-box** получает пакеты только через дескриптор (libbox `PlatformInterface`), поэтому поиск дескриптора остаётся в общем коде расширения, но теперь он обязателен только для адаптера sing-box. Реализация пишется заново: одноимённая функция в libbox — под GPL.
4. Очереди ограничены: выход ядро→устройство — кольцевой буфер фиксированного размера с отбрасыванием хвоста и счётчиком; вход — синхронный вызов, обратное давление через отложенный `readPackets`.

Следствия:

- Правило ADR-0003 §2 «Пакеты не проходят через Swift» в нынешней формулировке для Xray неверно. Точная формулировка: **Swift не обрабатывает пакеты — он переносит пачки между `packetFlow` и мостом, не разбирая их**. ADR-0003 нужно поправить (вне области этой правки).
- На каждый пакет приходится на два копирования больше, чем при чтении дескриптора. Цена на устройстве не измерена — это часть E-5.
- Сокеты самого ядра выводятся из туннеля не мостом, а платформой и конфигурацией (`tun-integration.md` §5).

## 5. Граница адаптера

Интерфейс движка в Swift исходит из наименьшего общего. Эскиз (имена предварительные):

```swift
public protocol TunnelEngine: Sendable {
    static var descriptor: EngineDescriptor { get }      // id, version, capabilities
    func start(config: EngineConfigBlob, tun: TunDescriptor, limits: EngineLimits) async throws
    func stop() async
    func snapshot() async -> EngineSnapshot              // traffic, connections, memory
    var events: AsyncStream<EngineEvent> { get }         // log lines, state changes, fatal exit
}
```

Типы `Libbox*`, конверт `Invoke`, имена полей JSON движков выше адаптера не поднимаются. Всё, что есть только у одного движка (группы выбора sing-box, Clash API, `PlatformInterface`), остаётся внутри его адаптера либо выражается через `EngineDescriptor.capabilities`.

## 6. Последствия

- Нужен Mac-сборщик с двумя версиями Go (для sing-box — та, которой собирает upstream; для Xray — ≥ 1.27).
- Проект поддерживает собственный Go-код (мост Xray) — риск R-12.
- Проверка конфигурации движком и замер задержки до подключения недоступны из приложения — риск R-15.
- `Dual` требует в приложении двух расширений с общим Swift-кодом и разными Go-артефактами.
- Первый вертикальный срез делается на Xray: нет GPL, нет форка gomobile, есть tvOS. Порядок обратим.

## 7. Что остаётся доказать на Mac

До закрытия этих пунктов решение считается принятым условно.

| № | Эксперимент | Критерий | Если не выполнен |
|---|---|---|---|
| E-1 | Мост Xray: c-archive под `ios/arm64`, симулятор, `macos`, tvOS | XCFramework собирается из закреплённых версий; туннель пропускает TCP, UDP, DNS на iPhone | решение пересматривается целиком |
| E-2 | libbox с сокращёнными тегами | собирается цепочкой upstream; туннель работает на iPhone | вернуться к полному набору тегов upstream и измерить |
| E-3 | Два packet-tunnel-расширения в одном приложении на iOS и tvOS | установка, переключение через `providerBundleIdentifier`, On-Demand, поведение после перезагрузки; затем TestFlight | `Dual` снимается; остаются `XrayOnly` и `SingBoxOnly` как два приложения |
| E-4 | Память | пиковый `phys_footprint` каждого движка под нагрузкой на самом старом поддерживаемом iPhone и на Apple TV; расширение не завершается по памяти | урезать теги и буферы; при неудаче — движок не заявляется на этой платформе |
| E-5 | utun: `packetFlow` и fd | Xray в режиме `flow` пропускает TCP, UDP, DNS через `readPackets`/`writePackets` на всех поддерживаемых ОС; измерены пропускная способность, CPU и память против режима `fd`; перебор fd работает на iOS, macOS (app и system extension), tvOS | Xray остаётся на `flow`; sing-box без рабочего перебора fd на платформе не заявляется (KVC-путь исключён) |
| E-6 | visionOS | мост Xray собирается под SDK `xros` и поднимает туннель на Vision Pro | visionOS остаётся экспериментальным уровнем без туннеля (ADR-0005) |
| E-7 | Единый мост (необязательный) | sing-box на Go ≥ 1.27.3 с версиями модулей Xray собирается, проходит interop-тесты, память обоих ядер в бюджете | вариант A остаётся отклонённым |
| E-8 | Минимальная ОС для Go 1.27 | мост запускается на минимальных версиях из ADR-0005 | поднять минимум |
| E-9 | Остановка и сторож | принудительный отказ движка снимает туннель; серия быстрых start/stop не оставляет туннель без движка | остановка через завершение процесса становится штатной |
