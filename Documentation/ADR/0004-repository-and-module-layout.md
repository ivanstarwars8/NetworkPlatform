# ADR-0004. Структура репозитория и модулей

- Статус: **принято**
- Дата: 2026-11-24
- Основание: ADR-0001…0003, `LICENSE_AUDIT.md` §7 (вариант F), `Documentation/Research/reference-apps.md` §5.14–5.15

## 1. Контекст

В репозитории на дату решения есть корневой `Package.swift` (swift-tools-version 5.9), пустой каталог `Packages/` и документы. Манифест объявляет четыре модуля — `DomainModels`, `CoreAbstraction`, `ConfigurationEngine`, `RoutingEngine` — каталогов которых ещё нет. `.gitignore` уже исключает `*.xcframework/`.

Референсы показывают, чего избегать: один xcodeproj без пакетов (sing-box-for-apple), закоммиченный блоб 51,8 МБ и сгенерированный код в git (hiddify), проект, который не собирается из собственного репозитория (Karing).

## 2. Решение

### 2.1. Один корневой `Package.swift`

Весь Swift-код библиотек — цели одного пакета в корне. Вложенных пакетов и отдельных манифестов на модуль нет.

Каждая цель лежит в `Packages/<Name>/`:

```
Packages/<Name>/Sources/…    код цели <Name>
Packages/<Name>/Tests/…      тестовая цель <Name>Tests
```

Манифест задаёт пути явно (`path: "Packages/<Name>/Sources"`), как уже сделано вспомогательной функцией `lib(_:deps:)`.

### 2.2. Модуль создаётся только вместе с настоящим кодом

- Каталог модуля и его запись в `Package.swift` появляются в одном изменении с первым содержательным кодом и хотя бы одним тестом.
- Пустых модулей, заглушек «на будущее» и файлов-заполнителей нет.
- **Манифест перечисляет только существующие модули.** Сейчас он объявляет четыре цели без каталогов, и пакет в таком виде не разрешится. Это надо исправить тем изменением, которое добавит первый код: либо создать модуль с кодом, либо убрать его из манифеста.
- Перечень ниже — карта намерений, а не список к созданию.

### 2.3. Карта модулей

| Модуль | Назначение | Зависит от | Появляется, когда |
|---|---|---|---|
| `DomainModels` | типы профиля, узла, транспорта, квоты; схема и миграции (ADR-0002) | — | пишется модель |
| `ConfigurationEngine` | компиляторы под движки, `ConversionReport`, `EngineCapabilities` | `DomainModels` | пишется первый компилятор |
| `CoreAbstraction` | протокол `TunnelEngine`, `EngineDescriptor`, типы состояния и статистики (ADR-0001 §5) | — | пишется первый адаптер |
| `RoutingEngine` | модель правил маршрутизации и пресеты как данные | `DomainModels` | пишется маршрутизация |
| `ProfileImport` | разбор ссылок, подписок, чужих форматов | `DomainModels` | пишется первый импортёр |
| `TunnelIPC` | конверт сообщений и `TunnelChannel` (ADR-0003) | `CoreAbstraction` | пишется расширение |
| `TunnelHost` | общий код расширения: получение utun fd, сетевые настройки, сторож, снимок конфига | `CoreAbstraction`, `TunnelIPC` | пишется расширение |
| `EngineXray` | адаптер моста Xray | `CoreAbstraction`, бинарная цель моста | собран мост |
| `EngineSingBox` | адаптер libbox | `CoreAbstraction`, бинарная цель libbox | собран libbox |

Имена первых четырёх совпадают с уже объявленными в манифесте. Остальные — предварительные.

Правила зависимостей:

1. `DomainModels` и `CoreAbstraction` не зависят ни от чего в проекте.
2. Ничто, кроме `EngineXray` и `EngineSingBox`, не импортирует модули движков.
3. Модули, которые линкует приложение, не зависят от `Engine*` и от `TunnelHost` — прямое следствие правила «приложение не линкует Go».
4. `EngineSingBox` не импортируется ничем, кроме цели расширения sing-box. Это одновременно техническая и лицензионная граница: если владелец выберет лицензию по модулям (ADR-0006, вариант F), GPL локализуется в этом каталоге.
5. Код из GPL-источников в общие модули не копируется (ADR-0006, временные правила).

### 2.4. Бинарные артефакты движков

- XCFramework в git не хранится. `.gitignore` это уже обеспечивает.
- Адаптеры подключают артефакты как `binaryTarget`. Для локальной разработки — по пути в каталоге артефактов; для выпуска — по URL с контрольной суммой.
- **Чистые Swift-модули должны собираться и тестироваться без артефактов движков.** Цели, требующие XCFramework, добавляются в манифест условно — только если артефакт есть на диске. `Package.swift` — программа на Swift, проверка наличия файла в нём возможна. Работоспособность этого приёма с Xcode и SwiftPM не проверена.

### 2.5. Остальные каталоги

Создаются, когда появляется содержимое:

| Каталог | Содержимое |
|---|---|
| `Apps/` | проект Xcode: приложения, расширения, entitlements, xcconfig по вариантам сборки (`XrayOnly`, `SingBoxOnly`, `Dual`) и каналам (App Store, Developer ID) |
| `Engines/XrayBridge/` | Go-модуль моста: `go.mod` с закреплёнными версиями, экспортируемый C-заголовок, скрипты сборки |
| `Engines/SingBox/` | только рецепт сборки libbox: SHA sing-box, версия Go, версия форка gomobile, список тегов, патчи upstream. Исходников sing-box в репозитории нет |
| `Documentation/` | ADR, исследования |
| `Tests/Interop/` | описания interop-тестов и эталонные конфигурации серверов (`PROTOCOL_MATRIX.md` §7) |

Цели приложений и расширений живут в проекте Xcode, а не в пакете: им нужны entitlements, Info.plist и подпись. Проект Xcode содержит минимум кода — точки входа; логика — в пакете.

### 2.6. Что не попадает в git

- XCFramework и любые собранные бинарники;
- сгенерированный код, если он воспроизводится сборкой;
- ключи, DSN, идентификаторы команд — подставляются конфигурацией, для которой в репозитории лежит шаблон.

Критерий открытости: клон репозитория и документированные шаги дают собираемое приложение.

## 3. Последствия

- `swift build` и `swift test` для чистых модулей работают на любом Mac без Go; логика модели и компиляторов тестируется без устройства.
- Один манифест растёт вместе с проектом; условное подключение бинарных целей усложняет его.
- Сборка движков — отдельный шаг с собственным тулчейном, не часть `swift build`.
- Проект Xcode нужен с момента появления первого расширения.

## 4. Что не доказано

- Условные бинарные цели в корневом манифесте корректно обрабатываются Xcode и SwiftPM на всех платформах.
- XCFramework, собранный `gomobile bind`, и XCFramework из c-archive одинаково подключаются как `binaryTarget`.
- Разделение на `XrayOnly` / `SingBoxOnly` / `Dual` выражается только xcconfig, без дублирования целей.
- Пакет с `platforms`, включающими visionOS, собирается при отсутствии среза visionOS в XCFramework движка.
