# ADR-0003. Плоскости управления, данных, наблюдаемости и безопасности; IPC между приложением и расширением

- Статус: **принято**; выбор транспорта IPC — обратимый, скрыт за одним протоколом
- Дата: 2026-11-24
- Основание: `Documentation/Research/singbox.md` §3.4–3.7, `Documentation/Research/reference-apps.md` §2.3 и §4–5, `PLATFORM_MATRIX.md` §2, §4, §8

## 1. Контекст

Приложение и расширение — разные процессы с разными бюджетами и временем жизни. Расширение запускает система, в том числе без приложения (On-Demand). Референсы решают связь между ними четырьмя разными способами, и у каждого есть описанные дефекты:

- sing-box-for-apple: gRPC libbox по unix-сокету в App Group; на tvOS — TCP на loopback с секретом; для system extension — XPC, отдающий fd. Go-рантайм живёт и в приложении. [V]
- hiddify: gRPC на loopback TCP с фиксированными портами; mTLS включается наличием файла; на iOS два экземпляра ядра; была утечка каналов на каждый resume. [V]
- Karing: Clash API ядра по HTTP и WebSocket с секретом. [V]
- OneXray: три вызова libXray из расширения и `handleAppMessage`. [V]

TN3120 называет локальный листенер в packet tunnel неподдерживаемым сценарием. [V]

## 2. Плоскости

| Плоскость | Где живёт | За что отвечает | Чего не делает |
|---|---|---|---|
| **Управление** | приложение (Swift) | профили, импорт, компиляция конфигурации (ADR-0002), выбор движка, `NETunnelProviderManager`, On-Demand, сведение состояний | не трогает пакеты; не линкует Go |
| **Данные** | расширение: Swift-хост и Go-движок | utun ↔ движок ↔ сеть; сетевые настройки туннеля; реакция на смену сети, сон, давление памяти | не разбирает профили; не строит и не чинит конфиг |
| **Наблюдаемость** | источник — расширение, потребитель — приложение | счётчики, соединения, память, журнал, диагностический пакет, отчёты о конвертации | ничего не отправляет с устройства без явного согласия |
| **Безопасность** | сквозная | хранение секретов, защита снимка конфигурации, границы IPC, санирование журналов и диагностики | не выводит режим защиты из побочного состояния (наличие файла и т. п.) |

Ключевые правила плоскости данных:

- **Пакеты не проходят через Swift.** Движок читает и пишет utun сам; `NEPacketTunnelFlow.readPackets` не используется. Так устроены все референсы. [V]
- `NEPacketTunnelNetworkSettings` формирует Swift-хост из данных адаптера.
- Наблюдение за сетью — `NWPathMonitor` в Swift-хосте; движку передаётся событие.
- Сторож, сериализация вызовов и аварийная остановка — как в ADR-0001 §4.

Ключевое правило плоскости управления: **состояний два, и они независимы** — туннель Network Extension и движок внутри него. Источник истины о туннеле — `NEVPNStatus`: он переживает перезапуск приложения. Состояние движка приходит по IPC. Control plane сводит их в одну модель и обязан уметь показать «туннель поднят, движок не отвечает».

## 3. IPC: решение

### 3.1. Каналы

| Назначение | Механизм | Основание |
|---|---|---|
| Жизненный цикл | `NETunnelProviderManager`, `startVPNTunnel(options:)`, `stopVPNTunnel`, уведомления `NEVPNStatus` | системный API на всех пяти платформах [V] |
| Команды и запросы | `NETunnelProviderSession.sendProviderMessage` ↔ `handleAppMessage` с версионированным конвертом | есть на всех пяти платформах [V]; не требует общего контейнера и сетевого сокета |
| Статистика | опрос тем же каналом, пока интерфейс на экране | одна реализация для всех вариантов упаковки |
| Журнал | расширение пишет кольцевой файл у себя; приложение читает страницами тем же каналом | не зависит от доступа к общему контейнеру |
| Конфигурация | в `startVPNTunnel(options:)`; расширение сохраняет снимок у себя | проверенная схема sing-box-for-apple на iOS, tvOS и обоих вариантах macOS [V] |

**Сетевые сокеты для связи приложения с расширением не используются.** Ни loopback TCP, ни HTTP, ни gRPC наружу расширения.

### 3.2. Конверт сообщений

```swift
struct TunnelRequest:  Codable { var version: UInt16; var id: UInt64; var body: Body }
struct TunnelResponse: Codable { var version: UInt16; var id: UInt64; var result: Result<Payload, TunnelError> }
```

- Версия протокола проверяется обеими сторонами: приложение и расширение обновляются вместе, но расширение прежней версии может ещё работать.
- Набор команд минимален: состояние, снимок статистики, страница журнала, перезагрузка конфигурации, сброс сети, выбор узла (если движок умеет), сбор диагностики.
- Каналом владеет один объект в приложении. Опрос идёт только при видимом интерфейсе и останавливается в фоне. Мёртвых и дублирующих опросов быть не должно.
- Над каналом — один протокол Swift (`TunnelChannel`). Замена транспорта не затрагивает вызывающий код.

### 3.3. Конфигурация и запуск системой

1. Приложение компилирует профиль (ADR-0002), подставляет секреты из Keychain и передаёт готовый документ в `startVPNTunnel(options:)` вместе с идентификатором движка и хэшем.
2. Расширение сохраняет снимок последнего успешно запущенного конфига в **своём** хранилище с явно заданным классом защиты файла.
3. При запуске без опций (On-Demand, переключатель в Настройках) расширение читает снимок.
4. On-Demand включается только при подключении пользователем и снимается при отключении — иначе система поднимет туннель после ручной остановки.

Снимок принадлежит расширению, а не лежит в App Group, потому что доступ system extension на macOS к пользовательскому контейнеру группы не подтверждён.

### 3.4. Внутренние интерфейсы движков

- Интерфейсы движка (command server libbox, Clash API, API статистики Xray) — деталь адаптера. Приложение к ним не обращается.
- Clash API и подобные HTTP-интерфейсы по умолчанию выключены.
- Если адаптеру sing-box для статистики нужен command server libbox, он поднимается на unix-сокете в контейнере расширения, клиент — в том же процессе. TCP-вариант не используется.
- Мост Xray отдаёт статистику и журнал прямыми вызовами C ABI, без сервера.

### 3.5. Что отложено

Добавляется только по результатам измерений:

- unix-сокет в App Group или XPC для потоков с высокой частотой (живой список соединений, журнал в реальном времени);
- уведомления от расширения к приложению без опроса;
- сопряжение устройств (передача профиля на Apple TV). Требование зафиксировано уже сейчас: канал с аутентификацией и шифрованием, локальный сервер только на время сопряжения. Схема Karing (HTTP без шифрования, эндпоинты без проверки токена) — пример того, как нельзя.

## 4. Плоскость безопасности

- **Секреты** (UUID, ключи, пароли узлов, токены подписок) хранятся в Keychain. Модель профиля хранит ссылки. Группа `group.*` одновременно служит keychain access group. [V]
- **Расширение секреты из Keychain не читает** — получает их в составе скомпилированного конфига. Это снимает зависимость от недоказанного доступа system extension к keychain.
- **Снимок конфигурации** содержит секреты в открытом виде, как того требует движок. Защита — класс защиты файла и песочница расширения. Это осознанный компромисс (риск R-14).
- **Журнал и диагностический пакет** санируются до записи: адреса серверов, идентификаторы и ключи заменяются. Пользователь видит содержимое пакета до отправки. Ключей шифрования диагностики, вшитых в приложение, нет.
- **Режимы защиты задаются явно** и проверяются.
- **Никакого удалённого управления поведением приложения**: удалённого конфига, удалённого JavaScript, обходов для ревью.

## 5. Плоскость наблюдаемости

Минимальный набор из расширения:

- трафик вверх и вниз, число соединений;
- `phys_footprint` процесса — собственная телеметрия Swift-хоста, не только то, что сообщает движок;
- состояние движка и причина последней остановки;
- журнал с уровнями; временный уровень trace с автоматическим возвратом, срок хранится в расширении и действует без приложения.

В приложении: отчёты о конвертации, пошаговая проверка сети, диагностический пакет одним действием. Телеметрия за пределы устройства — только по явному согласию.

## 6. Последствия

- Один транспорт на все платформы и варианты упаковки на первом этапе; меньше кода и меньше поверхности атаки, чем у любого референса.
- Потоки с высокой частотой на первом этапе недоступны или ограничены частотой опроса.
- Снимок конфигурации отражает последний запуск: правка профиля не действует на On-Demand, пока пользователь не переподключится. Интерфейс должен это показывать.
- На tvOS снимок может быть удалён системой; холодный запуск On-Demand тогда завершается понятной ошибкой, а не туннелем без движка.

## 7. Что не доказано

| Вопрос | Как проверить |
|---|---|
| Предельный размер и частота `sendProviderMessage`; поведение при приложении в фоне | замер на iOS, tvOS, macOS (оба варианта) |
| Предельный размер `options` в `startVPNTunnel` для больших конфигов | запуск с конфигом на тысячи узлов |
| Достаточно ли системной привязки `sendProviderMessage` к приложению-контейнеру как аутентификации, включая system extension | чтение документации и тест с посторонним процессом на macOS |
| Чтение снимка при On-Demand до первой разблокировки устройства | тест после перезагрузки для выбранного класса защиты |
| Сохранность снимка на tvOS | длительный тест на Apple TV |
| Стоимость command server libbox внутри расширения по памяти; можно ли получить статистику без него | измерение в рамках ADR-0001, E-2 и E-4 |
| Работа unix-сокета в контейнере на tvOS (upstream там использует TCP, причина неизвестна) | тест на Apple TV |
