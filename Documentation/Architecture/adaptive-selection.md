# Адаптивный выбор: сервер, транспорт, движок

Дата: 2026-11-25. Модуль: `Packages/AdaptiveBalancer`. Зависимостей нет (ни от других модулей пакета, ни внешних).

Статус: **написано и проверено тестами на Linux** (Swift 5.10.1, контейнер `swift:5.10`). На платформах Apple не собиралось. К управляющему слою, расширению и движкам модуль **не подключён** — это слой решений, а не работающая функция (раздел 12).

Пометки: **[V]** — проверено запуском тестов или чтением исходника (путь указан); **[U]** — не проверено.

## 1. Что это и чего здесь нет

Модуль отвечает на один вопрос: «какую конфигурацию использовать сейчас и почему». На вход — замеры, на выход — решение с объяснением.

Чего в модуле нет намеренно:

- часов и таймеров: время передаёт вызывающий (`Instant`), модуль системное время не читает;
- ввода-вывода: замеры делает не он, решения применяет не он;
- случайности: одинаковые входы в одинаковом порядке дают одинаковые решения **[V]** (`PropertyTests.testSameSeedGivesSameDecisions`);
- типов движков: идентификаторы `EngineID`, `TransportID`, `ServerID` — непрозрачные строки (ADR-0001 §5).

Тип `AdaptiveBalancer` — значение (`struct`, `Sendable`). Его можно копировать, сравнивать прогоны, гонять в тестах без ожиданий.

Идентификаторы попадают в объяснения, а объяснения предназначены для журнала. Поэтому идентификатор обязан быть непрозрачным токеном (UUID, номер), а не адресом сервера или именем хоста (ADR-0003 §4).

## 2. Три уровня

Конфигурация — тройка `Candidate(engine, transport, server)`. Три координаты — три уровня решения. Они вычисляются в фиксированном порядке и не смешиваются:

| Уровень | `SwitchLevel` | Что меняется | Цена | Когда рассматривается |
|---|---|---|---|---|
| (а) | `.server` | сервер; движок и транспорт те же | переподключение к другому узлу | всегда, первым |
| (б) | `.transport` | протокол/транспорт внутри того же движка (сервер тоже может смениться) | то же плюс другой тип рукопожатия; запас и выдержка строже | только если (а) ничего не изменил |
| (в) | `.engine` | движок | **перезапуск расширения туннеля, обрыв всех соединений** | только если (а) и (б) не могут удовлетворить профиль |

«Не могут удовлетворить профиль» определено строго: **ни у одного кандидата текущего движка автомат защиты не замкнут** (либо у профиля вообще нет кандидатов для текущего движка). Автомат размыкается только отказами (раздел 5). Отсюда главный инвариант:

> Изменение замеров задержки, джиттера, потерь или пропускной способности само по себе никогда не приводит к перезапуску туннеля.

**[V]** `EngineSwitchTests.testLatencyDegradationAloneNeverRestartsTheTunnel` (текущий движок безнадёжно медленный, другой идеален, отказов нет — 1500 шагов без перезапуска), `PropertyTests.testLatencyOnlyInputNeverRestartsTheTunnel` (24 случайных прогона по 2500 шагов), `PropertyTests.testEngineIsLeftOnlyWhenNoInEngineBreakerIsClosed`.

Порядок уровней тоже проверен: если на уровне (а) есть оправданная замена, она выбирается, даже когда кандидат уровня (б) выглядит лучше **[V]** (`SelectionTests.testServerLevelIsEvaluatedBeforeTransportLevel`); при отказе сначала идёт другой сервер, потом другой транспорт, и только потом движок **[V]** (`EngineSwitchTests.testInEngineAlternativesAreUsedBeforeAnEngineSwitch`).

### Сессии при смене движка не сохраняются

Смена движка — это остановка одного расширения и запуск другого (ADR-0001 §3: один движок на процесс, горячей смены нет). Все TCP-сессии, QUIC-соединения и незавершённые запросы, шедшие через туннель, обрываются. Модуль этого не скрывает и нигде не обещает обратного:

- `Change.requiresTunnelRestart` и `Decision.requiresTunnelRestart` равны `true` ровно для уровня `.engine`;
- это записано в документации `SwitchLevel.engine`, `Change`, `EngineSwitchCost`, `AdaptiveBalancer`;
- текст объяснения такого решения содержит фразу об обрыве соединений **[V]** (`testEngineSwitchAfterSustainedOutage`, `testFailedEngineSwitchRollsBackToThePreviousEngine`).

Управляющий слой не должен показывать смену движка пользователю как «бесшовную».

## 3. Входные данные

- `CandidateDescriptor` — кандидат, его `weight` и `priority`. Вызывающий передаёт только кандидатов, которые удовлетворяют профилю (протокол поддержан этим движком, разрешён пользователем). Модуль кандидатов не придумывает.
- `ProbeSample` — одно наблюдение: успех с `ProbeMeasurement` либо отказ с `FailureKind`. Все поля замера необязательны: RTT, время установления соединения, время TLS, доля потерь, пропускная способность. Пропускную способность мерить дорого, поэтому она необязательна везде.
- `NetworkClass` — `wifi`, `cellular`, `wired`, `unknown`.
- `Instant` — момент на монотонной шкале, секунды.

Некорректные значения (отрицательные, NaN, бесконечность) отбрасываются по полям, сам исход при этом учитывается **[V]** (`MetricsTests.testInvalidFieldsAreDroppedButOutcomeCounts`).

## 4. Оценка качества соединения

Решение никогда не принимается по одному пингу.

**Сглаживание.** По каждому кандидату и каждому классу сети ведутся экспоненциальные скользящие средние (EWMA) с числом учтённых отсчётов: RTT, джиттер (сглаженный модуль разности соседних RTT; через отказ разность не берётся), потери, время соединения, время TLS, пропускная способность, доля отказов. Один выброс сдвигает среднее только на долю `alpha` **[V]** (`testOneOutlierMovesTheAverageOnlyByAlpha`).

**Нормировка.** Каждая метрика отображается на 0…1 между «хорошим» и «плохим» концом шкалы (`ScoreScale`); пропускная способность — логарифмически. Метрики без данных выпадают, веса остальных перенормируются **[V]** (`testMissingMetricsDropOutAndWeightsRenormalise`).

**Доверие.** `confidence = n / (n + k) · 0,5^(возраст / T)`: растёт с числом отсчётов, падает с возрастом последнего. По умолчанию `k = 4`, `T = 300 с`.

**Итог.** `score = prior + confidence · (measured − prior)`, шкала 0…100, `prior = 40`. Неизмеренный кандидат получает ровно `prior`; один удачный пинг даёт доверие 0,2 и не может обогнать хорошо измеренного кандидата **[V]** (`testSinglePingCannotOutrankAWellMeasuredCandidate`); устаревший замер сползает к `prior` **[V]** (`testConfidenceGrowsWithSamplesAndDecaysWithAge`).

Дополнительно добровольная цель обязана иметь не меньше `minimumTargetSamples` отсчётов (3–6 в зависимости от уровня и сети) **[V]** (`testSinglePingNeverCausesASwitch`).

`ScoreBreakdown` хранит вклад каждой метрики — это часть объяснения.

Шкалы и веса по умолчанию выбраны рассуждением, **не измерением на устройствах [U]**. Способ замера задержки до подключения и его соответствие задержке через движок — открытый вопрос R-15 (`ROADMAP.md`, Phase 4).

## 5. Отказы: автомат защиты

У каждого кандидата на каждом классе сети свой `CircuitBreaker`. Его входы — только исходы (успех/отказ); задержка до него не доходит.

| Состояние | Смысл | Переход |
|---|---|---|
| `closed` | пригоден | N отказов подряд, либо сглаженная доля отказов выше порога при достаточном числе отсчётов → `open` |
| `open(until:)` | не выбирается и не зондируется | по времени → `halfOpen`; результаты, пришедшие в этот период, игнорируются |
| `halfOpen(successes:)` | для трафика не выбирается; нужны пробы | M успехов подряд → `closed`; первый отказ → `open` с удвоенной длительностью (до предела) |

Счётчик срабатываний забывается после долгого стабильного периода. **[V]** `CircuitBreakerTests` (6 тестов).

`probePlan(now:)` сообщает вызывающему, кого зондировать и зачем: `recovery` (полуоткрытый автомат), `probation`, `unmeasured`, `stale`. Кандидаты с разомкнутым автоматом в план не попадают. Сам модуль ничего не зондирует.

## 6. Стратегии

| Стратегия | Как ранжирует | Добровольная смена |
|---|---|---|
| `lowestLatency` | оценка с весами, где доминирует RTT | по запасу |
| `highestThroughput` | доминирует пропускная способность (если измерена) | по запасу |
| `maxStability` | доминируют доля отказов, потери, джиттер | по запасу |
| `balanced` | сбалансированные веса | по запасу |
| `weighted` | сбалансированная оценка × относительный вес кандидата | по запасу |
| `failover` | по `priority`; **липкая** | никогда: уход только при отказе, автоматического возврата нет |
| `manualPriority` | по `priority`; **вытесняющая** | всегда к самому приоритетному пригодному, оценка не учитывается |

`weighted` детерминирована: один туннель использует один выход, поэтому вес смещает выбор, а не распределяет трафик случайно.

**[V]** `SelectionTests`: `testLowestLatencyAndHighestThroughputChooseDifferently`, `testWeightedStrategyBiasesByWeight`, `testFailoverStrategyIsSticky`, `testManualPriorityReturnsToTheTopCandidate`; `PropertyTests.testAllStrategiesKeepTheInvariants`.

## 7. Защита от дребезга

| Механизм | Параметр | Что делает |
|---|---|---|
| Гистерезис | `LevelPolicy.hysteresisMargin` | добровольная смена — только если цель лучше текущего на запас; у транспорта запас больше, чем у сервера |
| Минимальная выдержка | `LevelPolicy.minimumDwell` | текущий кандидат должен проработать не меньше этого времени |
| Остывание | `SelectionPolicy.returnCooldown` | к только что покинутому кандидату нельзя добровольно вернуться (нет A→B→A) |
| Ограничение частоты | `SelectionPolicy.rateLimit` | жёсткий предел числа смен внутри движка в скользящем окне — и добровольных, и вынужденных |
| Испытательный срок | `ProbationPolicy` | пока новая конфигурация на испытании, добровольных смен нет |

Вынужденная смена (текущий кандидат непригоден) обходит запас, выдержку и остывание, но **не** ограничение частоты. Следствие, принятое сознательно: при исчерпанном лимите балансировщик остаётся на неработающем кандидате до конца окна и объясняет это (`noAlternative`, блокер `rateLimited`). Это цена гарантированной границы.

Граница колебаний: в любом окне `rateLimit.window` — не больше `maximumSwitches + 1` смен внутри движка; «+1» — откат, который лимитом не блокируется, но в нём учитывается. Для перезапусков туннеля — то же с `engineSwitch.rateLimit`.

**[V]** `PropertyTests.testOscillationIsBoundedByTheRateLimits` (50 случайных прогонов по 2500 шагов, Wi-Fi и сотовая сеть, с отказами серверов и целых движков), `testVoluntarySwitchesRespectDwellProbationAndCooldown`, а также сценарии дребезга: частое чередование задержек — 0 смен за 720 переворотов; малая амплитуда — 0 смен; редкое и большое чередование — смены есть, но в пределах лимита; чередующиеся отказы — без лавины.

## 8. Смена движка: условия и модель цены

Уровень (в) срабатывает, только когда выполнено **всё**:

1. текущая конфигурация непригодна, и уровни (а), (б) ничего не изменили;
2. ни у одного кандидата текущего движка автомат не замкнут (карантин и остывание здесь не считаются: это не свидетельства отказа);
3. смена движков разрешена политикой текущего класса сети;
4. на другом движке есть пригодный кандидат;
5. простой длится не меньше `max(minimumOutage, cost.expectedDowntime)` — перезапускать туннель ради простоя короче самого перезапуска убыточно;
6. цель измерена внетуннельными пробами не меньше `minimumTargetSamples` раз (`requireTargetEvidence`);
7. выгода покрывает цену: `score(цель) − cost.totalPenalty ≥ minimumNetBenefit`;
8. с прошлого перезапуска прошло не меньше `minimumInterval`;
9. не исчерпан лимит перезапусков в окне.

Модель цены `EngineSwitchCost` явная и в тех же единицах, что оценка:

```
totalPenalty = expectedDowntime · downtimePenaltyPerSecond + connectionResetPenalty
```

`expectedDowntime` — ожидаемое время без связи при перезапуске расширения; `connectionResetPenalty` — плата за обрыв всех соединений. Значения по умолчанию (3 с / 5 с простоя) — **предположение [U]**: реальное время перезапуска расширения на устройстве не измерялось (ADR-0001 §7, E-3).

Если условие не выполнено, решение — «оставить», а в объяснении перечислены **все** невыполненные условия уровня (в) сразу.

Частный случай: у профиля не осталось ни одного кандидата для текущего движка (профиль изменили). Ждать и сравнивать не с чем, поэтому условия 5–7 не применяются; интервал и лимит действуют.

Начальный выбор движка — не гонка задержек: при заданном `PolicySet.preferredEngine` другие движки рассматриваются, только если у предпочтительного нет пригодных кандидатов **[V]** (`testInitialSelectionHonoursPreferredEngineOverScore`).

**[V]** `EngineSwitchTests` (13 тестов): каждое условие блокирует по отдельности; счётчик простоя сбрасывается, когда кандидат в движке восстановился; на сотовой сети перезапуск наступает через 45 с простоя против 20 с на Wi-Fi.

## 9. Wi-Fi и сотовая сеть

`PolicySet` содержит две независимые политики; `wired` использует политику Wi-Fi, `unknown` — сотовую (более осторожную).

| Параметр | Wi-Fi | Сотовая |
|---|---|---|
| запас, сервер / транспорт | 10 / 20 | 15 / 25 |
| выдержка, сервер / транспорт | 30 / 120 с | 60 / 180 с |
| минимум отсчётов цели | 3 / 5 | 4 / 6 |
| остывание | 120 с | 300 с |
| лимит смен внутри движка | 4 за 600 с | 3 за 900 с |
| отказов подряд до размыкания | 3 | 4 |
| первое размыкание | 30 с | 45 с |
| испытательный срок | 20 с | 30 с |
| простой до смены движка | 20 с | 45 с |
| цена перезапуска | 3 с · 5 + 10 = 25 | 5 с · 5 + 15 = 40 |
| интервал между перезапусками | 300 с | 600 с |
| лимит перезапусков | 2 в час | 1 в час |

Обоснование: на сотовой сети RTT шумнее, кратковременные провалы радиоканала обычны, каждое переподключение стоит батареи и тарифицируемого трафика. Числа — отправная точка **[U]**, не результат измерений.

Замеры, автоматы защиты и последняя рабочая конфигурация ведутся **раздельно по классам сети**: измеренное на Wi-Fi ничего не говорит о сотовой сети **[V]** (`testMeasurementsAndBreakersAreKeptPerNetworkClass`, `testCellularPolicyIsMoreConservativeThanWiFi`). История смен (лимиты частоты) общая.

## 10. Последняя рабочая конфигурация и откат

Любая применённая конфигурация (включая начальную) проходит испытательный срок.

- **Пройден**: окно истекло, успехов не меньше `minimumSuccesses`, автомат замкнут → конфигурация становится последней рабочей (`lastKnownGood`).
- **Провален**: `failureThreshold` отказов в окне; либо автомат разомкнулся; либо вызывающий сообщил `reportApplyFailure` (движок не принял конфигурацию, расширение не запустилось); либо окно истекло, а успехов меньше требуемого (конфигурация не доказала работоспособность).

При провале конфигурация уходит в карантин (`quarantine`, по умолчанию 300 с), а балансировщик возвращается к последней рабочей — `ChangeKind.rollback`. Откат не блокируется выдержкой, остыванием и лимитом частоты. После отката испытательного срока нет: последняя рабочая конфигурация уже подтверждена.

Откат не выполняется, если последняя рабочая конфигурация сама непригодна (автомат не замкнут) — тогда идёт обычный вынужденный выбор.

Откат между движками возможен **только как отмена смены движка**: если испытание провалила конфигурация, полученная сменой сервера или транспорта, а последняя рабочая — на другом движке, перезапуска не будет. Откат смены движка — это ещё один перезапуск туннеля, и решение говорит об этом прямо.

Смена класса сети перезапускает окно испытания: успехи на Wi-Fi не подтверждают конфигурацию на сотовой сети.

**[V]** `RollbackTests` (13 тестов).

## 11. Объяснение решения

`decide(now:)` всегда возвращает `Decision` с `Explanation`:

- `reason` — машинный код (`improvement`, `failover`, `rollback`, `engineSwitch`, `inProbation`, `probationPassed`, `currentRetained`, `noAlternative`, …);
- `summary` — одна фраза с решающими числами;
- `blockers` — по каждому уровню: почему он ничего не изменил (`insufficientMargin`, `dwellNotElapsed`, `targetCoolingDown`, `targetNotProven`, `rateLimited`, `stickyStrategy`, `inEngineSatisfiable`, `outageTooShort`, `costExceedsBenefit`, …) с числами в `detail`;
- `current`, `chosen`, `candidates` — оценка каждого кандидата с разбивкой по метрикам, состоянием автомата, признаками карантина и остывания.

Все типы решения — `Codable`. **[V]** `PropertyTests.testEveryDecisionIsExplained`, `SelectionTests.testExplanationCarriesNumbersAndSurvivesCoding`.

## 12. Как этим пользоваться и что не сделано

```swift
var balancer = AdaptiveBalancer(candidates: descriptors, policies: .standard(preferredEngine: "…"), network: .wifi)
balancer.record(.success(candidate, at: now, ProbeMeasurement(rttMillis: 42)))
let decision = balancer.decide(now: now)
if let change = decision.change {
    // применить; при неудаче — balancer.reportApplyFailure(now:)
    // change.requiresTunnelRestart == true → все соединения будут оборваны
}
```

`decide` фиксирует результат: после возврата `Change` балансировщик считает цель текущей и ставит её на испытание.

Не сделано, и модулем не решается:

- **Нет зондировщика.** Кто и как меряет RTT, потери и время рукопожатия (через API движка или вне туннеля) — не реализовано. Для уровня (в) нужны внетуннельные пробы кандидатов другого движка.
- **Нет исполнителя.** Смена сервера и транспорта внутри работающего движка требует поддержки в адаптере движка; смена движка — в управляющем слое (ADR-0001, E-3). Ничего из этого модуль не вызывает.
- **Нет сохранения состояния.** Состояние живёт в памяти; последняя рабочая конфигурация между запусками не сохраняется (тип `LastKnownGood` — `Codable`, хранилища нет).
- **Числа по умолчанию не откалиброваны** на устройствах и реальных сетях.
- **Сборка на Apple не проверялась**; режим Swift 6 и release-сборка не проверялись.
- Встроенные балансировщики движков не используются и с ними модуль не согласован. Для справки **[V]**: в sing-box группа `urltest` имеет `tolerance` (по умолчанию 50) и интервал проверки — `/root/.cache/np-research/sing-box/protocol/group/urltest.go:253`; в Xray есть стратегия `leastLoad` с `Baselines`/`Expected` — `app/router/strategy_leastload.go:86`, и наблюдатель — `app/observatory/`. Код оттуда не заимствован (ADR-0006 §5). Кто из двух — встроенный балансировщик движка или этот слой — управляет выбором внутри движка, предстоит решить отдельным ADR.
