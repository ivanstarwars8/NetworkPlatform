# Маршрутизация: соответствие RoutingEngine и маршрутизатора Xray

Дата: 2026-11-25. Движок: Xray-core, модуль `github.com/xtls/xray-core v1.260327.1-0.20261109052709-676eaf66f8f0` (тот же, что закреплён в мосте). Файлы маршрутизатора в этом коммите побайтно совпадают с исследовательским клоном `e17392a` из `Documentation/Research/SOURCES.txt` (сверено `md5sum` десяти файлов `app/router`, `common/geodata`, `features/routing/dns`, `infra/conf/router.go`).

Пометки: **[V]** — прочитано в исходнике (путь указан) или получено запуском; **[U]** — не проверено.

## 1. Разделение труда

Решение: **маршрутизирует движок. Swift не стоит на пути данных.**

| Кто | Что делает | Когда |
|---|---|---|
| Движок (Xray `app/router`) | выбирает исходящий для каждого соединения | на каждом соединении, в процессе расширения |
| `RoutingEngine` (Swift) | хранит модель правил; проверяет её; понижает деревья условий до плоских правил (`RuleLowering`); отвечает «куда пойдёт это соединение и почему» (`RouteSimulator`); ищет затенённые правила (`ConflictDetector`) | при редактировании и компиляции профиля, в приложении |
| Компилятор конфигурации движка (адаптер) | записывает плоские правила синтаксисом движка | при компиляции профиля |

Следствия:

- `CompiledRouter.match` в расширении не вызывается. Ни пакет, ни соединение не проходят через Swift (ADR-0003); правило не вычисляется дважды.
- Источник истины один — `RoutingTable`. Конфиг движка получается из неё через `RuleLowering.lower`, симулятор отвечает по ней же. Чтобы эти два ответа не расходились, семантика Swift приведена к семантике движка (§3) и сверяется дифференциальным тестом (§5).
- Таблица, у которой `LoweredTable.isLossless == false`, движку не отдаётся: правило без плоской формы в `rules` отсутствует, и маршрутизация отличалась бы от показанной симулятором. Это ошибка компиляции с отчётом (ADR-0002), а не предупреждение.
- Счётчики срабатываний правил в работающем туннеле — дело движка (у каждого плоского правила есть тег `r<номер>.<часть>`, Xray возвращает его как `ruleTag`), а не `HitCounters`: тот остаётся для симуляции.
- Балансировку внутри группы выполняет движок. Симулятор останавливается на «группа X».

Компилятора плоских правил в JSON Xray в репозитории ещё нет. Его прототип — функция `xrayRule` в `Benchmarks/RoutingParity/parity_test.go`; именно она проверена тестом.

## 2. Как маршрутизирует Xray

Всё **[V]**, пути относительно корня Xray-core.

- **Порядок.** Правила просматриваются по порядку, побеждает первое совпавшее (`app/router/router.go`, `pickRouteInternal`). Самый длинный префикс, специфичность домена и т. п. роли не играют.
- **Внутри правила — И.** `BuildCondition` (`app/router/config.go`) складывает заданные поля в `ConditionChan`, `Apply` требует истинности всех (`app/router/condition.go`). Правило без полей — ошибка `this rule has no effective fields`.
- **Внутри поля — ИЛИ.** Список доменов, адресов, портов, тегов — совпадение любого.
- **Домены.** Четыре типа: `full:` (равенство), `domain:` (имя или поддомен по границе метки), `keyword:` (подстрока; это же тип по умолчанию для значения без префикса — `infra/conf/router.go`, `ParseDomainRules(..., Domain_Substr)`), `regexp:` (Go `regexp`, поиск без якорей). Значения `full/domain/keyword` приводятся к нижнему регистру (`common/geodata/domain_matcher.go`, `parseDomain`); шаблон — нет. Имя запроса приводится к нижнему регистру и больше никак не нормализуется (`condition.go`, `DomainMatcher.Apply`).
- **Приоритет типов** `full > domain > keyword > regexp` (`common/geodata/strmatcher/strmatcher.go`) определяет только порядок индексов в `Match`; маршрутизатор зовёт `MatchAny`, результат которого от приоритета не зависит. На выбор маршрута приоритет типов не влияет.
- **Два сопоставителя доменов.** `newDomainMatcherFactory` выбирает по ОС: на iOS и Android — `CompactMphDomainMatcherFactory` (для правил, записанных в конфиге, линейный сопоставитель), иначе `MphDomainMatcherFactory`. Сборка для Apple использует первый, тест на Linux — второй; поэтому харнесс отдельно сверяет их между собой (§5).
- **geosite / geoip.** `geosite:xx` и `geoip:xx` — ссылки на записи файлов `geosite.dat` / `geoip.dat`, читаются движком при построении правила (`common/geodata/rule_parser.go`, `geodat_loader.go`). Атрибуты (`@ads`) фильтруют записи.
- **Адреса.** `IPMatcher.Apply` берёт адреса назначения из контекста и зовёт `AnyMatch`: достаточно одного адреса из списка. У соединения с доменом адресов нет (`features/routing/session/context.go`, `GetTargetIPs`). Отрицание `!cidr` собирается в отдельное множество с `reverse = true` (`common/geodata/ip_matcher.go`, `buildOptimizedIPMatcher`): все отрицаемые префиксы правила — одно множество, условие «адрес вне всего множества». Две особенности: при пустом списке адресов результат ложен; адрес семейства, префиксов которого в множестве нет, не совпадает никогда (`matchAddr`: `max4 == 0xff` → `false` до учёта `reverse`).
- **domainStrategy.** `AsIs` — домен не разрешается. `IPOnDemand` — контекст оборачивается в `ResolvableContext`, и первое же адресное правило получает адреса из DNS; удачный ответ DNS заменяет исходный адрес назначения, неудачный оставляет его (`features/routing/dns/context.go`). `IPIfNonMatch` — сначала полный проход без разрешения; если ничего не совпало и домен есть — второй полный проход с разрешением (`router.go`, `pickRouteInternal`).
- **Порт, сеть.** Порт сравнивается со списком диапазонов; отсутствующий порт равен 0. Сеть — TCP или UDP; у соединения без сети назначение считается недействительным, и домен, адрес и порт пусты.
- **inboundTag, user** — точное сравнение, с учётом регистра; `user` допускает `regexp:`. Пустые элементы списков молча отбрасываются. **protocol** — префикс: `strings.HasPrefix(sniffed, value)`.
- **Прочие поля:** `sourceIP`, `sourcePort`, `localIP`, `localPort`, `vlessRoute`, `attrs`, `process`, `localOS`, `webhook`.
- **Нет совпадения.** `PickRoute` возвращает `ErrNoClue`, диспетчер берёт исходящий по умолчанию — первый в конфиге (`app/dispatcher/default.go`). Отдельного «финального действия» нет. Если правило указывает несуществующий тег, соединение закрывается, а не уходит в исходящий по умолчанию (там же).
- **Балансировщики.** Правило указывает `balancerTag`; балансировщик выбирает среди исходящих, отобранных по префиксам `selector`, стратегией `random` (по умолчанию), `roundRobin`, `leastPing`, `leastLoad`; при пустом выборе — `fallbackTag`, иначе ошибка и исходящий по умолчанию (`app/router/balancing.go`, `config.go`).

## 3. Расхождения и что с ними сделано

### 3.1. Исправлено в Swift (семантика приведена к движку)

| № | Было в RoutingEngine | В Xray | Что сделано |
|---|---|---|---|
| F1 | у имени запроса отрезалась завершающая точка | имя сравнивается как пришло: `example.com.` не попадает под `domain:example.com` **[V, запуск]** | `RouteRequest` только приводит имя к нижнему регистру. В правилах точка по-прежнему отрезается — это нормализация при компиляции |
| F2 | условие по отсутствующему порту ложно | отсутствующий порт равен 0, правило `0-1023` совпадает **[V, запуск]** | отсутствующий порт и порт источника равны 0 |
| F3 | один адрес назначения, DNS не моделировался | `AsIs` / `IPIfNonMatch` / `IPOnDemand`, несколько адресов, «любой из» | `RoutingTable.domainStrategy`, `RouteRequest.resolvedIPs`; один или два прохода, как в `pickRouteInternal`; `RouteDecision.usedSecondPass`; симулятор объясняет второй проход |
| F4 | отрицание адреса только как `not(ipCIDR)`: истинно при отсутствии адреса | `!cidr` ложно без адреса, множество общее, семейство без префиксов не совпадает | новое условие `ipNotIn([IPCIDR])` с семантикой движка, включая обе особенности. `not` остался булевым и в движок не компилируется (D1) |
| F5 | нет условий по источнику, входящему, пользователю, протоколу | есть | `sourceCIDR`, `sourcePort`, `inboundTag`, `user`, `sniffedProtocol` (префикс) |
| F6 | «финальное действие» без оговорок | финального действия нет | `RuleLowering` добавляет замыкающее правило «сеть TCP или UDP»; для `ipIfNonMatch` — не добавляет (оно совпало бы на первом проходе, и второй, с DNS, не случился бы) и требует сделать финальное действие исходящим по умолчанию |
| F7 | дерево `and`/`or` произвольной формы | одно правило = И полей, поле = ИЛИ значений | `RuleLowering`: ДНФ; `or` по разным полям → несколько подряд идущих правил с тем же действием (`r7.0`, `r7.1`, …) |
| F8 | `domainSuffix(".example.com")` — только поддомены | у `domain:.example.com` два сопоставителя Xray формально описаны по-разному (`DomainMatcher.Match` против trie в группе); на Linux запуск дал «только поддомены» **[V, запуск]** | на значение с точкой не полагаемся: понижается в `regexp:^.+\.example\.com$` |

Изменённые ожидания существующего теста: `RouterTests.testDomainRules` — два утверждения о завершающей точке (F1). Раньше: имя запроса `WWW.EXAMPLE.COM.` совпадает с правилом и нормализуется в `www.example.com`. Теперь: не совпадает, точка сохраняется. Других правок существующих тестов нет.

### 3.2. Различия, оставленные намеренно

| № | Различие | Почему оставлено |
|---|---|---|
| D1 | `not` в Swift есть, в движке нет | для симуляции и поиска конфликтов удобно; при понижении — отказ `negation`, молчаливой потери нет |
| D2 | И двух условий одного поля (`and([suffix, keyword])`) в Swift вычисляется, в одно правило движка не записывается | отказ `sameFieldConjunction` |
| D3 | регулярные выражения: `LinearRegex` — подмножество RE2 (нет `\b`, POSIX- и Unicode-классов, не-ASCII, флагов кроме ведущего `(?i)`) | шаблон вне подмножества — ошибка компиляции таблицы; в движок попадает только то, что Swift умеет вычислить сам. Обратного расхождения (Swift принял, Go отверг) в корпусе нет |
| D4 | наборы правил только встроенные; `geosite:` / `geoip:` в модели нет | симулятор не может ответить за содержимое `.dat`, которого у него нет. См. §4 |
| D5 | префикс `::ffff:a.b.c.d/96+` Swift хранит как IPv4-префикс; Xray такую запись отвергает (`parseCIDR`: длина больше 32 для IPv4) **[V, чтение]** | в плоское правило попадает уже нормализованная запись `a.b.c.d/N`; запрос с `::ffff:`-адресом оба считают IPv4 **[V, запуск]** |
| D6 | действие `chain` | в маршрутизаторе Xray цепочек нет; компилятор должен синтезировать исходящий с `proxySettings`/`dialerProxy` и сослаться на его тег. Не реализовано |
| D7 | действие `group` — без стратегии и состава | состав и стратегия живут в модели групп и в движке; `fallbackTag` требует `observatory`. В тесте проверено только: правило найдено то же, выбранный исходящий входит в группу |
| D8 | `user` — только точное сравнение | `regexp:` для пользователей не поддержан; значение с таким префиксом сравнивалось бы буквально, расхождение возможно. Компилятор обязан отвергать `user`, начинающийся с `regexp:` **[U: проверки в коде ещё нет]** |
| D9 | нет `localIP`, `localPort`, `vlessRoute`, `attrs`, `process`, `localOS`, `webhook`, `script` | на клиенте Apple не нужны или недоступны; при импорте чужого конфига — непереводимый остаток |
| D10 | выключенное правило сохраняет номер | в движок не попадает; теги плоских правил несут исходный номер |

### 3.3. Известные расхождения на уровне запроса

Проверяются тестом: харнесс требует, чтобы они действительно расходились (иначе список устарел).

| № | Запрос | Swift | Xray | Обоснование |
|---|---|---|---|---|
| K1 | без сети (не TCP и не UDP) | вычисляет заданные поля | назначение недействительно: домена нет, порт 0 | у реального соединения сеть есть всегда; для симулятора это неполный ввод |
| K2 | имя длиннее 253 байт | имя отбрасывается | сравнивается как текст | не DNS-имя; предел защищает симулятор от импортированного мусора |
| K3 | имя с пробелом или управляющим символом | имя отбрасывается | сравнивается как текст | то же |

## 4. Чего не хватает до компиляции настоящих профилей

1. **geosite / geoip (D4).** Самый заметный пробел: реальные профили состоят из них. Предлагаемое решение: условие-ссылка на внешний набор, которое понижается в поле домена/адреса как непрозрачное значение и передаётся движку как есть; симулятор для такого условия отвечает «не определено» (третье состояние) либо читает `.dat` сам. Не реализовано.
2. Компилятор плоских правил в конфиг Xray как модуль пакета (сейчас — прототип в Go-харнессе).
3. Отказ на `user` с префиксом `regexp:` (D8).
4. Цепочки (D6) и состав групп (D7).
5. sing-box: его маршрутизатор с Swift не сверялся **[U]**. Семантика RoutingEngine теперь — семантика Xray; для sing-box потребуется такая же сверка, и часть решений (F1, F2, F4) может не совпасть.

## 5. Дифференциальный тест

Состав:

- `Packages/RoutingEngine/Tests/ParityCorpus.swift` — детерминированный генератор (LCG с фиксированным зерном) таблиц и запросов и рукописные таблицы `edge-cases`, `known-differences`.
- `Benchmarks/RoutingParity/testdata/corpus.json` — корпус: плоские правила, запросы и решение Swift (`CompiledRouter.match`) для каждого запроса. Формат нейтральный, синтаксиса движка в нём нет.
- `EngineParityTests.testStoredCorpusIsCurrent` — сохранённый корпус равен свежесгенерированному; при изменении семантики тест падает, пока корпус не перегенерирован (`NP_PARITY_WRITE=1`) и Go-харнесс не прогнан заново.
- `EngineParityTests.testLoweredRulesAreEquivalentToTheTable` — три вычислителя Swift (индексный, линейный эталон, плоские правила после понижения) согласны на всех таблицах корпуса.
- `Benchmarks/RoutingParity/parity_test.go`, `TestParity` — переводит плоские правила в объект `routing` Xray, разбирает его штатным `infra/conf.RouterConfig`, поднимает `app/router.Router` через `Init`, для каждого запроса строит штатный контекст сессии (`features/routing/session`) и зовёт `PickRoute`. Сравнивает номер правила (по `ruleTag`) и исходящий. DNS и менеджер исходящих — подставные: DNS отдаёт `resolvedIPs` запроса, пустой список означает ошибку разрешения.
- `compact_test.go`, `TestCompactDomainMatcherAgrees` — каждый список доменов корпуса строится обеими фабриками сопоставителей (обычной и той, что используется на iOS) и сверяется на всех именах запросов.

Запуск:

```sh
# Swift: сверка корпуса (и перегенерация с NP_PARITY_WRITE=1)
Tools/swift-docker.sh swift test -j 1 --filter EngineParityTests
# Go, на сервере разработки
Tools/remote-go.sh 'cd Benchmarks/RoutingParity && PARITY_OUT=parity-result.json go test -run . -v ./...'
```

Результаты прогона — в §6.
