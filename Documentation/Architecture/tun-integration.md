# Путь пакета между NEPacketTunnelProvider и Xray-core

Дата: 2026-11-25. Закреплённая версия ядра: **Xray-core v26.11.9**, коммит `676eaf66f8f05d4d558ee7a74b4736623d3feeb9`
(в `Cores/Bridge/go.mod` — `v1.260327.1-0.20261109052709-676eaf66f8f0`), Go 1.27.4.

Пометки: **[V]** — прочитано в исходнике закреплённой версии (путь от корня модуля ядра) либо в коде моста;
**[M]** — измерено или проверено тестом на сервере разработки (Linux/amd64), команда и журнал указаны в §9;
**[U]** — не проверено: по памяти о документации Apple либо требует устройства. Ничего в этом документе не
запускалось на платформах Apple.

## 1. Что есть в ядре

1. **Собственный TUN-inbound есть, tun2socks не нужен.** `proxy/tun` — обработчик `protocol: "tun"` и
   собственный пользовательский стек TCP/IP (без gVisor): `stack.go`, `tcp_lightweight.go`, `udp_fullcone.go`,
   `packet.go`. IPv4, IPv6, TCP, UDP, ICMP Echo. [V: `proxy/tun/README.md`, `proxy/tun/stack.go`]
2. **Режим готового дескриптора на Darwin есть.** Если задано окружение `xray.tun.fd`, `NewTun` дублирует
   дескриптор (`F_DUPFD_CLOEXEC`), ставит non-blocking, ждёт чтения через kqueue и читает/пишет пакеты с
   четырёхбайтным заголовком utun (семейство адресов). Оригинал дескриптора остаётся у вызывающего.
   [V: `proxy/tun/tun_darwin.go:147-177, 272-310`, `common/platform/platform.go:27`]
   Тот же ключ работает на Linux и Android. [V: `proxy/tun/tun_linux.go:247-298`]
3. **Стек отделим от устройства.** Экспортированы `tun.NewStack`, `tun.StackOptions`, интерфейс `tun.Tun`
   (`ReadPacket`/`WritePacket`) и метод `Stack.Input(packet []byte)` — «принимает пакет от tun, который
   пакеты передаёт сам, а не читается»; пакет не удерживается, вызывать можно из нескольких потоков.
   [V: `proxy/tun/stack.go:21-33, 208-211`, `proxy/tun/tun.go:7-17`]
   Это и есть точка, в которую можно подать пакеты из `NEPacketTunnelFlow`, не имея дескриптора.
4. Обработчик `tun.Handler` из ядра устройство подменить не даёт: `Start()` всегда вызывает платформенный
   `NewTun`. [V: `proxy/tun/handler.go:126-130`] Поэтому для пути без дескриптора мост регистрирует
   собственный inbound поверх `tun.NewStack` (§3).

## 2. Как получить дескриптор utun на Apple и почему это не основной путь

У `NEPacketTunnelProvider`/`NEPacketTunnelFlow` нет публичного свойства с файловым дескриптором. [U — по
памяти о заголовках SDK; в этой сессии SDK не открывался] Известные способы:

| Способ | Что это | Статус |
|---|---|---|
| KVC `packetFlow.value(forKeyPath: "socket.fileDescriptor")` | обращение к приватному свойству | приватный API, **не используем** |
| перебор fd 0…N, `getpeername` + сравнение с `com.apple.net.utun_control` | публичные системные вызовы, но опора на недокументированное устройство NetworkExtension (приём WireGuardKit) | недокументировано; риск R-08 |

Оба способа опираются на недокументированное. Документированный интерфейс один: `NEPacketTunnelFlow`
`readPackets(completionHandler:)` / `writePackets(_:withProtocols:)` — обе операции уже пакетные (массив
пакетов за вызов). [U]

**Решение.** Основной путь для моста Xray — документированный `packetFlow` с пакетной (batch) передачей в
Go (режим моста `tun.mode = "flow"`). Путь через дескриптор (`tun.mode = "fd"`) мост поддерживает, потому что
ядро умеет его само и это ничего не стоит, но включается он только явной опцией и только после проверки на
устройстве (ADR-0001 §7, E-5). Для sing-box дескриптор по-прежнему обязателен — это отдельный адаптер.

## 3. Режим `flow`: документированный путь

```
ядро iOS ── utun ── NetworkExtension
                       │ readPackets → [Data]            (1 вызов = пачка пакетов)
                Swift: склеить пачку в один буфер
                       │ npb_tun_write(buf, len)         (1 переход Swift→Go на пачку)
                Go:  flowDevice.writeBatch → tun.Stack.Input(пакет) для каждого кадра
                       │ стек ядра: TCP-соединения, UDP-потоки
                     flowInbound.HandleConnection → routing.Dispatcher.DispatchLink → outbound
                       ⋮
                     стек ядра → flowDevice.WritePacket → ограниченная очередь (кольцевой буфер)
                       │ npb_tun_read(buf, cap, timeout) (1 переход на пачку, блокируется в Go)
                Swift: разобрать кадры → writePackets([Data], protocols)   (1 вызов на пачку)
```

Реализация: `Cores/Bridge/engine/flowtun.go`, `packetqueue.go`. [V]

- **Конфигурация та же, что и для fd.** Компилятор конфигурации выдаёт обычный inbound `protocol: "tun"`.
  В режиме `flow` мост вынимает его из конфигурации до `core.New` и регистрирует вместо него свой
  `inbound.Handler` с тем же тегом, MTU, `userLevel` и настройками sniffing; счётчики
  `inbound>>>тег>>>traffic>>>…` те же. Правила маршрутизации по `inboundTag` не меняются. [V: `engine/config.go`
  `resolveTun`, `engine/flowtun.go` `flowInbound`]
- **Формат пачки** (в обе стороны): последовательность кадров `uint16 LE длина` + IP-пакет. Семейство адресов
  не передаётся — берётся из старшего полубайта пакета. [V: `engine/packetqueue.go`]
- **Вход (устройство → ядро).** `npb_tun_write` синхронный: возвращается, когда все пакеты пачки прошли
  `Stack.Input`. `Input` не блокируется на медленном получателе: TCP ограничен объявленным окном
  (256 КиБ на соединение [V: `proxy/tun/tcp_lightweight.go:31`]), UDP — очередью потока в 1024 пакета с
  отбрасыванием [V: `proxy/tun/udp_fullcone.go:168, 38-45`]. Обратное давление на систему естественное:
  Swift вызывает следующий `readPackets` только после возврата `npb_tun_write`; пока он не вызван, пакеты
  стоят в очереди utun ядра. Буфер пачки после вызова не удерживается (стек может менять байты на месте).
- **Выход (ядро → устройство).** `WritePacket` стека никогда не блокируется: пакет копируется в кольцевой
  буфер фиксированного размера (`tun.outQueueBytes`, по умолчанию 2 МиБ); если места нет — пакет
  отбрасывается и считается (`txDropped`). Для TCP это обычная потеря, на которую реагирует управление
  перегрузкой стека. Блокировать нельзя: `WritePacket` вызывается и изнутри `Input` (ACK, SYN-ACK), то есть
  на потоке Swift. Очередь на один пакет не аллоцирует.
- **Чтение.** Один выделенный поток Swift крутит `npb_tun_read(buf, cap, -1)`; вызов спит в Go до появления
  пакета и забирает всё, что накопилось и помещается в буфер. Остановка движка будит его кодом `closed`.
- **Копирования.** Вход: `Data` → буфер пачки (Swift) → буферы стека (Go). Выход: стек → кольцо → буфер
  вызывающего → `Data`. Это на два копирования на пакет больше, чем у fd-пути; цена измерена ниже.

Что измерено на сервере разработки (Linux/amd64, 5 vCPU; см. §9): [M]

| Что | Результат |
|---|---|
| Переход C→Go, 1 пакет на вызов | 258–266 нс на пакет |
| Переход C→Go, пачка 8 | 50 нс на пакет |
| Переход C→Go, пачка 64 | 32–35 нс на пакет (вызов ≈ 2,1–2,2 мкс) |
| Один TCP-поток «загрузка» через весь путь `flow` → freedom → loopback | 1,05–1,2 Гбит/с |
| Размер пачки, который складывается сам под нагрузкой (ядро → устройство) | в среднем 34–54 пакета, максимум 186 |
| Заполнение очереди выхода одним насыщенным TCP-потоком | 255–263 КиБ (окно стека); при очереди 256 КиБ потери 0,011 %, при 2 МиБ — 0 |
| 8 параллельных потоков через VLESS+REALITY+Vision | 740–810 Мбит/с, потерь в очереди 0 |

Вывод: стоимость перехода при пакетной передаче — десятки наносекунд на пакет; попакетные вызовы были бы в
~8 раз дороже. Очередь в 2 МиБ вмещает около восьми одновременно насыщенных TCP-соединений без потерь.
Цифры получены вызовом из C на x86-64; стоимость перехода Swift→Go на arm64 и поведение `readPackets` на
устройстве не измерялись. [U]

## 4. Режим `fd`

Мост кладёт дескриптор в окружение процесса (`xray.tun.fd`) на время работы движка и снимает при остановке;
JSON ради этого не правится. Дальше работает `tun.Handler` ядра: чтение `read()` по одному пакету с ожиданием
через kqueue, запись `write()` по одному пакету. [V: `engine/engine.go` `bringUp`, `proxy/tun/tun_darwin.go`]
Переходов между языками нет вовсе, но есть системный вызов на каждый пакет.

Состояние: на Linux режим `fd` проверен против настоящего стека TCP/IP ядра — tun-устройство в отдельном
сетевом пространстве имён, TCP по 8 МиБ и UDP (включая фрагментированную датаграмму 4000 байт) по IPv4 и
IPv6, счётчики inbound совпали с переданным байт в байт. [M: `Cores/BuildScripts/bridge-linux-netns-test.sh`]
**На Apple режим `fd` не запускался**; код чтения utun в ядре (`tun_darwin.go`) другой, чем на Linux. [U]

## 5. Исходящие соединения ядра и петли маршрутизации

Сокеты, которые ядро открывает к прокси-серверу, не должны попадать в туннель.

1. **NetworkExtension сам выводит соединения процесса-провайдера из его туннеля.** [U — утверждение из
   материалов Apple по Packet Tunnel; в исходниках не проверить, нужно подтвердить на устройстве] Если это
   так, ничего дополнительного не требуется.
2. **Привязка к интерфейсу средствами ядра.** `streamSettings.sockopt.interface` у outbound на Darwin
   ставит `IP_BOUND_IF` / `IPV6_BOUND_IF`. [V: `transport/internet/sockopt_darwin.go:136-147`] Это запасной
   путь, его выдаёт компилятор конфигурации; имя физического интерфейса должен сообщить Swift (NWPathMonitor)
   и при смене сети конфигурацию придётся применять заново.
3. `autoOutboundsInterface` TUN-inbound ядра (автоматическая привязка всех сокетов) работает только внутри
   `tun.Handler.Start` и только когда ядро само владеет tun. [V: `proxy/tun/handler.go:133-164`] В режиме
   `flow` он не действует; на iOS в режиме `fd` — тоже (индекс интерфейса берётся, но маршруты ядро не
   ставит). Полагаться на него не будем.
4. **`excludedRoutes`** в `NEIPv4Settings`/`NEIPv6Settings` для адресов сервера — документированный способ,
   но адрес должен быть известен до старта. [U]
5. Отдельный риск — **разрешение имени сервера**: если ядро разрешает имя прокси-сервера через системный
   резолвер, а системный DNS направлен в туннель, получится петля. [U] Исходная позиция: имя сервера
   разрешается до поднятия туннеля либо через серверы DNS, заданные в конфигурации с прямым outbound.

Мост сам сокеты не привязывает: это свойство конфигурации, а не моста.

Проверено на Linux (2026-11-27, `Cores/BuildScripts/bridge-tunlab.sh e2e`): маршрут по умолчанию v4/v6 в
tun, адрес сервера исключён маршрутом через veth (аналог `excludedRoutes`). За весь прогон насос не увидел в
tun ни одного пакета на адрес сервера; контрольный прогон с удалённым исключающим маршрутом даёт такие
пакеты (насос их отбрасывает) и соединение не поднимается. То есть ядро открывает сокеты по системной
таблице маршрутизации, и мост в туннель их не заворачивает. Как ведёт себя NetworkExtension (п. 1), этим
не проверяется. [M: `Documentation/Performance/bridge-benchmarks.md` §2]

## 6. MTU и фрагментация

- MTU берётся из `settings.mtu` tun-inbound, по умолчанию 1500 [V: `infra/conf/tun.go:79-80`]; опция моста
  `tun.mtu` его переопределяет в режиме `flow`. То же значение Swift обязан поставить в
  `NEPacketTunnelNetworkSettings.mtu`.
- TCP: MSS = MTU − заголовок IP − заголовок TCP, объявляется в SYN-ACK и уменьшается по MSS клиента.
  [V: `proxy/tun/tcp_lightweight.go:230-258, 371`] Сегменты никогда не фрагментируются.
- UDP: датаграмма больше MTU при записи в tun режется на IP-фрагменты, входящие фрагменты собираются.
  [V: `proxy/tun/stack.go:454-471`, `proxy/tun/packet.go:238-300`] Проверено тестом: UDP 3000 и 8000 байт
  при MTU 1500 и 1400, IPv4 и IPv6, в обе стороны, стек к стеку без прокси. [M]
- Через прокси (tun ядра Linux → мост → VLESS+REALITY+Vision → сервер) при MTU 1280/1400/1500 проходят
  датаграммы до 7500 байт, 7600 и больше теряются — у штатного xray так же, это предел ядра, не моста. DF:
  датаграмма MTU−28 (v4) / MTU−48 (v6) с DF проходит, на байт больше система отвергает (`EMSGSIZE`). Если
  MTU tun больше `tun.mtu` моста, TCP подстраивается по MSS, а ответы UDP стек режет на лишние фрагменты —
  значения должны совпадать. [M: `Documentation/Performance/bridge-benchmarks.md` §2]
- Прокси-транспорты здесь потоковые, инкапсуляции пакета в пакет нет, поэтому MTU туннеля не обязан быть
  меньше MTU физической сети. Больший MTU уменьшил бы число пакетов; на устройстве не пробовали. [U]

## 7. IPv4 и IPv6

Стек принимает оба семейства. Отбрасываются: IPv4-mapped IPv6, пакеты с loopback-адресом источника или
назначения, неуказанный адрес назначения, multicast-источник. [V: `proxy/tun/stack.go:219-226`] ICMP Echo
отвечает сам стек; остальные типы ICMP игнорируются. [V: `proxy/tun/README.md`] Чтобы IPv6 не утекал мимо
туннеля, Swift задаёт `NEIPv6Settings` с маршрутом по умолчанию; проверено только на уровне стека
(TCP и UDP по IPv6 через путь `flow`). [M]

## 8. DNS

1. Swift задаёт `NEDNSSettings` с адресом сервера, который маршрутизируется в туннель (и
   `matchDomains = [""]`, чтобы запросы шли в туннель [U]).
2. Запрос приходит обычным UDP-пакетом на порт 53 → стек → диспетчер → правило маршрутизации
   `inboundTag: [tun], port: 53 → outbound "dns"`.
3. Outbound `dns` отвечает на A/AAAA через встроенный DNS ядра; тот ходит к серверам из секции `dns`
   конфигурации, а правило по `dns.tag` отправляет эти запросы в прокси-outbound.
4. Поле `dns` самого tun-inbound на Darwin системный DNS не меняет. [V: `proxy/tun/README.md`]

Проверено тестом: DNS-запрос пакетом UDP/53 через путь `flow` → `dns`-outbound → встроенный DNS → через
VLESS+REALITY на сервер → локальный тестовый резолвер; ответ вернулся, прямой outbound не использовался. [M]
DoH/DoT, которые приложение делает само, этим путём не перехватываются.

## 10. Что остаётся доказать на устройстве

- `readPackets`/`writePackets` под нагрузкой: размеры пачек, задержка, пропускная способность, память.
- Что сокеты провайдера действительно не попадают в собственный туннель (§5, п. 1).
- Режим `fd` и его сравнение с `flow` по CPU и батарее (E-5).
- Поведение при смене сети (Wi-Fi ↔ сотовая) для обоих режимов.
- MTU больше 1500.
- Потолок загрузки ~200 Мбит/с, найденный на Linux у моста и у штатного xray одинаково
  (`bridge-benchmarks.md` §2): есть ли он на устройстве.
- Время жизни UDP-сессий стека ядра (`connIdle`, по умолчанию 300 с) и память под ними на устройстве
  (`bridge-benchmarks.md` §6).
